# 每天三次的增量与时效

默认 max_post_age_days=30、overlap_hours=24、catchup_days=7。不同产品数据目录隔离。用户不需填参数；需要调整时，在该数据目录 time-policy.json 写这些正整数。配置模板中的值供 agent 参考，脚本实际覆盖读取数据目录 time-policy.json。没有文件就使用默认值。不新建定时任务、不擅自指定三个钟点。

## 每次执行

1. run_state.py start 返回首次/后续、search_since/search_until、catchup_required 与可用的 catchup_since。since 保留原检查点供兼容，真正检索优先用 search_since。每天首轮按 Asia/Shanghai 判断，另查近7天；首次查近30天已包含补查范围，无需重复跑。
2. 查询按组合独立成功窗口；partial/failed 不推进全局。新查询回溯30天，未完成查询补旧窗口，不用本轮全局时间跳过。轮次跨夜仍按成功记录决定。
3. 浏览器搜索结果页有日期筛选就使用工具实际提供的日期范围；只有过去一天/一周选项时选覆盖所需窗口的较宽范围。after/before 等仅在当前工具实际支持并已验证时用，搜索时区和粒度可能不同，保留重叠，不自行把过滤日期当真实帖龄。
4. 正式结果本地去重；候选链接与评论 ID 保留。相同 URL 更新信息/最后发现而不新增行。不同 URL 的转载按原帖/采购编号/作者及文本人工审查，不能承诺 URL 去重能识别所有转载。同帖新评论只有确实找到独立评论链接或 ID 才当新需求，不能把旧视频重新发现算新客户。
5. 索引可能延迟，每天首轮近7天补查而非只查几小时间隔；延迟超过7天仍可能漏，必要时用户可扩大补查值。持续低产可以换查询，不用放开数年前帖子凑数。

## 日期证据与名单

published_at 保存搜索实际显示日期文字，published_observed_at 是看到该时间标签时的含时区时间；明确时区的发布日期可另存 published_at_iso。found_at 是发现时间，不能冒充发帖时间。相对“2小时前/11个月前”保留原文，脚本按观察时间与保守区间判断，不伪造精确时间；普通月/年显示不会按固定30天直接生成日期。日期边界含糊则待确认。

时效列：近期（搜索显示/未核验）、日期未知、日期待确认、日期异常。只有可以确定超出30天的记录不进当前名单，内部 candidates.json/leads.json 保留。候选脚本保存日期标签时会固定观察时间；相同链接重新发现不能把老帖重新变新。重新导出时重新计算帖龄，日期未知仍留名单，但不标本轮新需求。已知发布年份很旧但无法被脚本解析时由 agent 将有依据的日期录入，不能忽略反证。

报告只交付客户名单.csv，简述本轮真正新 URL、更新、累计和日期未知数量。预检记录、运行日志、过期台账不另作用户附件。日期过滤不会授权打开社媒原帖、登录或联系客户。
