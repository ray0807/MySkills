# 项目进度上报

整理当前项目的目标、进展、任务、测试与阻塞，补问缺失信息并上传，供用户的工作安排助手查询。

## 范围

只整理当前项目的实际工作信息。读取代码、文档、当前会话和已有记录作为证据；Git 状态仅用于判断本项目做过的变更，不展开仓库管理检查。

不要主动检查或处理 GitHub 发布、嵌套仓库、gitlink、提交推送、移动 `.git`、旧部署清理、Skill 安装同步等维护事项。只有用户明确将其指定为本项目目标或任务时，才记录。发现技术细节不等于用户有待办，不把自行发现的维护建议加入 tasks、nextActions 或 openQuestions。

调用本 Skill 只授权整理、补问、设置连接和上报，不授权修复代码、改 Git 配置、移动目录或管理部署。已有记录中混入的无关维护建议不应继续传播；保留用户明确要求的任务和仍有效的项目事实。此流程无需为安装、部署或仓库操作提出额外问题。

## 连接与 Key

项目连接保存在当前项目 `.project-hub/config.json`，属于本机私密配置，不上传、不提交 Git、不写入项目摘要。使用本 Skill 的 `scripts/hub.mjs` 管理和调用连接。相对路径从 Skill 目录解析；通过 `--project <项目绝对目录>` 明确目标。

- 服务地址固定为 `https://project.boomclaws.com`，上报 MCP 为 `/mcp/report`，查询 MCP 为 `/mcp/query`。不要询问、让用户选择或确认域名，不提供自建地址选项。脚本始终连接此服务，旧配置的 url 字段不参与地址选择。
- **每次调用本 Skill，第一步先检查当前项目是否保存有效 Key，然后询问本次 Key 选择，等待用户回答。** 不因以前已选择过、配置已存在或资料已齐全而跳过。回答前不要调用查询/上报 MCP，也不要生成或覆盖 Key；可以读取本地项目资料。
- 无论当前项目是否已有 Key，每次都问“本次新建 Key，还是复用 Key？”，提供“新建 Key”和“复用 Key”两个选项。选项只写名称，不附带真实 Key，不把“已有 key: <值>”当作选项，也不要求用户在选择项的 Other 中输入 Key。
- 用户选择“复用 Key”后，再单独询问“请输入你要复用的 API Key”，提供自由文本输入并等待。即使本机已有 Key，也不自动沿用，必须以用户本次输入为准。如果用户本次已经主动提供要复用的完整 Key，直接采用，不重复索取。
- 用户选择生成后运行 `node <skill>/scripts/hub.mjs generate --project <目录>`。使用密码学随机 Key，不用模型编造。
- 用户选择复用并输入后，校验 Key 为 24–256 个不含空格的可打印 ASCII 字符，通过 `set` 保存到当前项目配置；已有配置时使用 `set --replace`，保留项目 ID。可以让用户在本机终端交互输入，也可以接收聊天的自由文本输入后通过标准输入传给脚本，避免把 Key 放进命令参数。不允许未收到 Key 就查询或上传。
- 用户选择新建且已有配置时，用 `generate --replace`。若输入或生成的 Key 与原 Key 不同，简短说明“换 Key 就换用户，旧数据不迁移”。用户选择即已授权设置，不再重复要求确认。
- **每次调用结束，最终回复必须展示本次使用的完整 API Key，使用单独的纯文本代码块方便复制。新建、复用、输入、更换，以及查询或上传成功、失败，都执行同一规则。** 从当前项目 `.project-hub/config.json` 读取本次实际使用的 `apiKey`；刚生成的也可从脚本返回的 `API Key:` 获取。不得编造、遮盖或截断，不得只在工具输出展示，不得让用户去文件里找。不要以“用了当前保存的 Key”代替实际值，也不要因回复要简短而省略。
- 每次最终展示 Key 后提醒：“请复制并保存；其他项目和工作安排助手使用同一个 Key。” 新建或更换时再补充“换 Key 就换用户，旧数据不迁移”。即使已在中途展示，最终回复仍须包含 Key。若确实没有任何有效 Key 且用户拒绝生成，明确说明“尚未设置 API Key”，不能编造一个。
- 未完成 Key 选择或配置时，不擅自生成、不上报。服务地址已固定，缺少旧配置中的 url 字段不需要补问。

## 整理与反问

用稳定项目 ID，首次默认使用仓库名的字母数字、短横线形式，保存在本机配置中；避免每次产生新 ID。查询已有记录：`node <skill>/scripts/hub.mjs get --project <目录>`。查询失败时不得视为空项目并覆盖；报告故障，保留本地整理结果。明确不存在时再建新记录。

先从已有资料提取事实，不重复询问已有明确答案。对缺失或矛盾的信息分轮询问，每轮集中 2–3 个相关问题，优先目标、完成标准、当前阻塞。覆盖：

- 项目目标、使用者、背景、成功标准和验收条件；
- 当前阶段、必做功能、暂不做的范围、交付物；
- 已完成、正在做、待完成、待测试、已知缺陷与实际测试证据；
- 截止时间及其时区、里程碑、优先级、预计耗时；
- 任务依赖、阻塞、风险、需要用户做的决定及人工任务；
- 与本项目交付直接相关的技术与运行环境、协作者、下一步行动；仓库和部署地址已有资料可直接记录，不展开维护检查。

用户暂不确定或要求直接上报时，在 `metadata.openQuestions` 保留待确认问题，不无限追问。不猜测进度，不把未运行测试标成通过，不把计划当作完成。用户提供的耗时与进度估计标注来源。除非有明确依据，不强行填写估计数字或截止日期。

## 上传前最后一轮：人工事项进度

整理结束后、上传之前，根据当前项目具体事项，询问无法从代码、文件、工具结果或已有明确反馈中检测到的人工工作进度。能在项目中检测的信息由 AI 读取整理，不让用户重复核对。没有未知人工事项时直接上报，不为凑流程提问。

- 不笼统地固定询问“测试通过了吗”。只有实际使用测试或用户验收属于当前项目且无法检测时，才点明场景询问，例如“你在工作安排助手里配置查询 MCP 到哪一步了，是否已验证能读取全部项目？”。自动化测试结果仅代表实际检查，不推断人工验证也通过。
- 对需要用户操作且当前状态未知的事项，问“这项目前是未开始、进行中，还是已完成？”，不要直接宣布“下一步需要你做”。例如：“查询 MCP 的配置现在是未开始、正在配置，还是已配置并验证能读取全部项目？”
- 用户说“已经在做”就记为 `in_progress`，不记为 `todo`；说“已完成”就按其说明更新。已配置但尚未验证的事项，可将配置标完成，把验证标为待测试；不能把二者混为同一待办。
- 既有上报中的人工待办不代表仍未开始。核对后更新，不把旧待办原样作为新指令。未经用户确认的状态放在 `metadata.openQuestions`，不要强行写入已确认的 nextActions 或给用户分派工作。
- 使用前面已回答的信息，只补问仍未知的内容，通常合并成一轮 1–3 个问题，等待用户回答后再上传。用户明确要求不回答直接上报时，保留“待确认”，不要编造通过或未开始。
- 在 `testSummary` 中分清自动化检查与用户实际使用测试，标注用户反馈来源。必要时用 `metadata.userTesting` 保存场景、结果和未测试部分；上传用户确认后的 tasks、pendingTests、nextActions。

## 上传

参照 [references/report.md](references/report.md) 组装有效完整快照。以已有记录为基础更新，保留仍有效的任务、未解决的问题和扩展信息；字段缺省可能清空旧列表。不可包含 API Key、凭据、环境变量值或无关私密内容。

完成本次 Key 选择和最后一轮测试、人工任务核对后组装并上报，不输出“先确认 schema”等过程旁白，不在聊天粘贴完整 JSON、服务回包、命令日志或测试清单。用户调用本 Skill 已授权上报，不额外要求上传确认；有必要补问的答案仍应等用户回答。将快照存到 `.project-hub/report.json`，执行 `node <skill>/scripts/hub.mjs report --project <目录>`，通过 `/mcp/report` 的 `report_project` 上传。已有连接工具可直接使用，但须核实服务地址和身份一致。脚本通过 `/mcp/query` 的 `get_project` 获取旧数据，不依赖预先安装 MCP SDK。

只有收到成功响应才报告上传成功。失败时保留快照，简短说明故障，不宣称完成，不自动更换 Key。成功回复简短说明项目与上报结果、当前阶段和测试状态，另附完整 Key 与复制提醒。下一步只写用户已确认的未完成行动；正在做的标“进行中”，已完成的不再列为待办。不要重复叙述整份上报内容或提出“我可以帮你修复”的延伸建议。

每次调用的最终回复示例（替换为实际结果和 Key）：

````text
已上报「项目名称」。当前阶段：MVP 试用。
本次 API Key：
```text
<本次实际使用的完整 Key>
```
请复制并保存；其他项目和工作安排助手使用同一个 Key。
````

发送最终回复前检查：是否核对实际测试和人工任务状态，是否有本次实际 Key 的完整代码块和复制提醒。缺少内容先补齐，不用代码推测用户进展。Key 只用于连接配置与用户回复，不写入上报快照。
